# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나, 순서를 바꾸거나, 일부만 적용하지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 프로젝트별 규칙이 없을 때 쓰는 **기본값(fallback)** 이다.
- 두 규칙이 충돌하면 프로젝트 규칙을 따르고, 충돌하지 않는 부분은 이 파일을 적용한다.

## 적용 기준

### TDD를 반드시 적용한다

- 비즈니스 로직
- API (엔드포인트, 요청/응답 처리, 에러 매핑)
- 유틸 함수, 순수 함수
- 상태·데이터 변환 로직 (훅, 리듀서 등)
- **버그 수정** (먼저 버그를 재현하는 실패 테스트를 쓴다)

### TDD가 불필요하다

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업, 스타일)
- SQL (마이그레이션, 스키마)

경계가 모호하면 **적용하는 쪽으로 판단한다.**

## RED-GREEN-REFACTOR 사이클

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 테스트 하나에 여러 동작을 묶지 않는다.
- 테스트 이름은 기대 동작을 설명한다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 문법 오류, import 오류, 잘못된 셋업으로 인한 실패는 RED가 아니다. 테스트를 고쳐서 올바른 이유로 실패시킨다.
- 처음부터 통과하는 테스트는 아무것도 검증하지 않는다. 테스트를 고친다.

### 2. GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 지금 테스트가 요구하지 않는 기능, 분기, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 실행해서 확인한다.
- 다른 테스트가 깨지면 이번 변경이 원인이다. 먼저 고친다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 리팩터링 후 전체 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작이 남아 있으면 **RED로 돌아간다.**
- 모든 동작이 구현될 때까지 사이클을 반복한다.

## 삭제 강제 규칙

- 테스트보다 먼저 프로덕션 코드를 작성했다면 **그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 남겨 두면 테스트가 코드에 맞춰 쓰이게 된다.
- 삭제 후에는 테스트를 먼저 쓰고, 코드를 처음부터 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| 너무 단순해서 테스트가 불필요하다 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없다. 단순하다는 판단이 틀리는 지점에서 버그가 나온다. |
| 테스트는 나중에 추가하겠다 | 나중에 쓴 테스트는 구현을 그대로 따라 쓰게 된다. 바로 통과하므로 아무것도 증명하지 못한다. "나중"은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 재작업으로 더 많은 시간을 쓴다. 급할수록 사이클을 지킨다. |
| 이미 짠 코드를 삭제하면 낭비다 | 이미 쓴 시간은 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 더 크다. 다시 쓰는 건 빠르다. |
| 프로토타입이다 | 프로토타입은 버려질 때만 프로토타입이다. 대부분 그대로 운영 코드가 된다. 적용 대상이면 규칙도 적용된다. |

## 완료 전 확인

- [ ] 모든 새 동작에 대해 RED(실패 확인)를 거쳤는가
- [ ] 실패 이유가 "기능 미구현"이었는가
- [ ] GREEN 단계에서 요구된 것 이상의 코드를 쓰지 않았는가
- [ ] 신규+기존 테스트가 모두 통과하는가
- [ ] 테스트보다 먼저 쓴 프로덕션 코드가 남아 있지 않은가
