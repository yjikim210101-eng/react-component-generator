# commit: 변경사항 분석 후 컨벤션 커밋

작업 디렉토리의 변경사항을 읽고, 논리적 단위로 나눠, 한국어 커밋 메시지로 **승인을 묻지 않고 바로 커밋한다.**

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff HEAD
git log -5 --oneline
```

- `git diff HEAD`는 staged와 unstaged 변경을 함께 보여 준다.
- untracked 파일은 `git status`로 확인하고, 필요하면 내용을 읽는다.
- 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 종료한다.
- `git log`로 기존 메시지의 말투와 형식을 확인해, 이미 쓰는 관례가 있으면 그것을 우선한다.
- `.env`, 키, 토큰 등 비밀 정보 파일이 포함돼 있으면 커밋 대상에서 빼고 사용자에게 알린다.
- `node_modules`, `dist` 같은 빌드 산출물이 커밋 대상에 섞여 있으면 마찬가지로 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적이 섞여 있으면 나눈다.
- 분류 기준: 기능 추가, 버그 수정, 동작 변경 없는 구조 개선, 설정·문서·의존성.
- 같은 목적에 속한 파일(예: 컴포넌트와 그 스타일, 테스트)은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면, 대화형 옵션(`-i`, `-p`)은 쓸 수 없으므로 한 커밋으로 묶고 그 이유를 알린다.
- 변경이 한 가지 목적뿐이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문(선택)>
```

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 사용자에게 보이는 기능 추가 또는 변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `chore` | 설정, 의존성, 빌드, 문서 등 기타 작업 |

규칙:
- 요약은 한국어로, 50자 안팎의 한 줄로 쓴다. 마침표는 붙이지 않는다.
- 무엇을 했는지보다 **왜 필요한지**가 드러나게 쓴다. 파일명 나열은 피한다.
- 본문은 요약만으로 부족할 때만 쓴다. 한 줄 비우고, 이유와 영향 범위를 적는다.
- 코드 식별자와 기술 용어는 원문 그대로 쓴다.
- 환경에 지정된 커밋 attribution(공동 작성자) 줄이 있으면 본문 끝에 붙인다.

예시:

```
feat: 결과 카드를 데스크톱 창 스타일로 개선

삭제 버튼을 창 닫기 박스로 옮기고, 탭을 폴더 탭 모양으로 바꿨다.
```

### 4. 바로 커밋

1. 승인을 묻지 않고 분류한 순서대로 커밋한다. 파일은 **이름을 지정해서** 스테이징한다. `git add -A`, `git add .`는 쓰지 않는다.

```bash
git add <파일1> <파일2>
git commit -m "<type>: <요약>" -m "<본문>"
```

2. 커밋이 여러 개면 계획 순서대로 하나씩 만든다.
3. 끝나면 `git log --oneline -n <커밋 수>`로 만든 커밋의 메시지와 포함 파일을 보고한다.

## 하지 않는 것

- `git push`, `--amend`, `--no-verify`, `reset --hard` 같은 명령은 사용자가 명시적으로 요청하지 않으면 쓰지 않는다.
- pre-commit hook이 실패하면 우회하지 않는다. 원인을 설명하고 고친 뒤 **새 커밋**으로 다시 시도한다.
- 비밀 정보 파일과 빌드 산출물은 승인 여부와 상관없이 항상 커밋에서 뺀다.
- 기본 브랜치(`main`, `master`)에서 작업 중이면 새 브랜치를 만든 뒤 그 브랜치에 커밋한다.
